Case 01 / Graph intelligence

SupplyBeacon

Explainable supply-chain risk intelligence prototype

PythonFastAPINetworkXGraphRAGLangGraphReact
Live demo ↗Repository ↗
Project type: End-to-end research prototypeFocus: Explainability & decision supportBuild scope: Graph · API · Agent workflow · UI

01Evidence

The documented saved base-graph artifact contains 3,144 nodes and 9,350 edges, including products, suppliers, brands, warehouses and locations. The workflow combines graph relationships with retained weather/news evidence and a curated warehouse reference catalog.

The sources are not all equivalent: external observations, derived scores, simulated relationships and catalog references need to remain distinguishable.

02Insight

A warning by itself does not prove that a specific product is stocked at a warehouse or that the warehouse has suffered a disruption. Decision support needs inspectable relationship paths, evidence provenance, location context and timestamps—not an ungrounded answer from an LLM.

Catalog association is not inventory, and a deterministic risk index is not a calibrated probability.

03Solution

Build one evidence-tracing workflow around a file-backed NetworkX graph, transparent risk components, grounded GraphRAG/LangGraph retrieval and a Scenario Lab for exploring relationship-backed alternatives when a warehouse is disrupted.

The system aims to show why a result was returned and which evidence supports it.

04Execution

  • Connected a React/TypeScript interface to FastAPI endpoints.
  • Modelled products, suppliers, brands, warehouses, locations and events as typed graph entities and relationships.
  • Added source/freshness metadata, spatial and temporal eligibility checks, risk components and evidence-grounded query flows.
  • Documented backend and frontend validation workflows and regression-test areas.

05Impact & proof

3,144Nodes in saved base graph
9,350Edges in saved base graph
5Core evidence-to-answer stages
1Unified investigation workflow
Demonstrated technical outcome: the prototype brings graph paths, risk components, source context and scenario exploration into one reviewable workflow. This is a capability claim, not a measured reduction in supply-chain losses or investigation time.

↗Limitations & next step

The project README documents open correctness issues involving entity-scoped evidence retrieval, delivery-response mapping, warehouse ranking and network-summary semantics. These require targeted fixes and regression tests before operational use.

Next: test against verified, current inventory/event feeds; repair the documented defects; make validation reproducible from a clean checkout; and calibrate risk scores against labelled outcomes.

Case 02 / NLP & model evaluation

Employment Fraud Detector

Classifying potentially fraudulent job postings with text and structured signals

Pythonscikit-learnTF-IDFXGBoostDistilBERTStreamlit
Live demo ↗Repository ↗
Project type: End-to-end NLP applicationFocus: Imbalanced classificationTrade-off: Recall · precision · inference cost

01Evidence

The Fake Job Postings dataset contains 17,880 records: 17,014 genuine and 866 fraudulent postings. Fraud represents 4.84% of the dataset, so a model can achieve high accuracy while still missing many fraudulent posts.

Exploratory analysis also found that 32.7% of fraudulent postings had company logos compared with 81.9% of genuine postings. These are group-level associations, not proof that an individual post is legitimate or fraudulent.

02Insight

Accuracy alone is a weak success criterion when the positive class is rare. Fraud recall and F1 help reveal missed fraud and the trade-off between catching more risky posts and raising false alarms.

Text matters, but contextual clues such as missing company information or screening questions should be treated as signals—not as deterministic rules.

03Solution

Compare a lightweight TF-IDF + Logistic Regression baseline, XGBoost variants with structured features, and a fine-tuned DistilBERT model. Add trust-score and risk-explanation logic to make predictions easier to review.

Keep the deployed app lightweight while retaining the transformer model as a stronger experimental comparison.

04Execution

  • Handled missing values and combined job title, company profile, description, requirements and benefits into a text input.
  • Used TF-IDF to establish a fast, interpretable baseline.
  • Compared classic ML models and a DistilBERT transformer; reported results for accuracy, fraud precision, recall and F1.
  • Packaged the lightweight model in an interactive Streamlit application.

05Impact & proof

Reported project evaluation — DistilBERT:

99%Accuracy
91%Fraud precision
86%Fraud recall
88%Fraud F1
Deployment distinction: the public Streamlit demo uses TF-IDF + Logistic Regression. Its documented metrics are 97% accuracy, 88% fraud recall and 73% fraud F1. DistilBERT is the advanced comparison model, not the model serving the live demo.

↗Limitations & next step

These are documented dataset/model evaluation results, not external validation on current job-market traffic. A risk prediction is a screening signal and does not establish fraud by itself.

Next: evaluate on a fresh time-based dataset, inspect false negatives and false positives, test calibration and drift, and provide clear explanations without overclaiming certainty.

Case 03 / Predictive analytics

Loan Default Risk Classification

Credit-risk modelling with class imbalance and threshold analysis

PythonPandasLightGBMscikit-learnSMOTESHAP
Live app ↗Repository ↗
Project type: Collaborative MSc projectMy documented contribution: Data collection, preprocessing & EDAFocus: Default-class recall

01Evidence

The Home Credit Default Risk dataset contains 307,511 loan applications and 122 raw features. About 8.1% of records are defaults, creating an approximately 11.4:1 class imbalance.

The project notes substantial missingness in some property-related features and a right-skewed income distribution, requiring careful preprocessing and evaluation.

02Insight

Overall accuracy alone can hide the cost of missed defaults. A lower decision threshold can catch more risky applicants, but usually increases false positives. The right threshold depends on risk policy and the cost of each type of error.

The meaningful question is not simply “Which model is most accurate?” but “What trade-off does the model create for the decision-maker?”

03Solution

The team compared Logistic Regression, Random Forest and LightGBM, addressing imbalance with training-data SMOTE and class weighting. Feature engineering added financial ratios and age/employment signals; SHAP-based interpretation was part of the team workflow.

04Execution

My documented contribution: data collection, data preprocessing and exploratory data analysis. Model preparation/training, deployment, and interpretability were shared across teammates with separately documented responsibilities.

The workflow includes imputation, encoding, high-correlation review, domain-driven feature engineering, model comparison and threshold analysis.

05Impact & proof

Reported LightGBM results at the default threshold:

89.5%Accuracy
0.768ROC-AUC
54.0%Default recall
0.75855-fold mean ROC-AUC (±0.0043)
Threshold experiment: at the selected threshold of 0.1027, reported recall increased to 71.3% while precision was 14.1%. This makes the recall–false-alarm trade-off explicit; it is not a production lending recommendation.

↗Limitations & next step

This is an offline academic dataset, not a live lending service. The reported metrics do not establish fairness, regulatory compliance or performance on a current applicant population.

Next: verify threshold selection on a dedicated validation set, preserve an untouched test set, calibrate probabilities, conduct fairness analysis and assess the actual cost of false approvals versus false rejections.
